# Kawu — Full Feature Roadmap v1.1

## 全阶段功能规划（用于评估与排期，非最终承诺范围）

> **使用说明**：Phase 1 是当前要开发的 MVP，功能已锁定。Phase 2-4 是**方向性规划**，
> 用于帮助评估整体产品空间和长期投入规模，具体是否开发、何时开发、最终形态如何，
> 取决于前一阶段的真实验证结果。**不要把 Phase 2-4 的功能清单当作产品承诺或对外宣传内容。**
>
> 产品原则参见《Kawu Product Document》"产品原则"一节，本文档不重复维护，
> 避免两份文档各自维护一份原则清单、日后改动不同步的问题。唯一在此重申的一条：
>
> **默认私有原则：每一份报告默认保持私有，除非经纪主动、逐份选择分享。**
> 这条原则贯穿全部四个阶段，Phase 3/4 的任何分享功能都建立在这条原则之上，不是取代它。

# Phase 1 — Showing Intelligence（MVP，现在开发）

**目标**：验证买方经纪是否会每次带看都用，是否愿意把报告发给客户。

## 核心录制流程

1. 一键开始/结束带看
2. 自然语音输入，无需固定格式
3. 照片/视频拍摄，自动关联时间点
4. 语音标记（Voice Tag）
5. 自动保存原始媒体

## AI 处理流程

6. 语音转文字（中英双语）
7. 房间/空间自动识别
8. 结构化信息提取（优点/缺点/顾虑/待跟进）
9. AI 生成带看总结草稿
10. 草稿状态标记，需经纪确认后才能发送

## 编辑与审核

11. 报告编辑器
12. 转写纠错
13. 敏感内容提示（主观/风险表述标记）

## 客户交付

14. 生成客户版报告（PDF / 分享链接）
15. 品牌自定义（经纪 logo、联系方式）
16. 多渠道发送（微信、邮件、短信链接）—— **这个安全分享链接机制是 Phase 2 Buyer Portal 决策的先验证对象**，见下方 Phase 2B 说明

## 客户与房源管理

17. 私有工作台
18. 客户关联
19. 多套房源对比视图
20. 房源历史记录（同房源多次带看独立版本）
21. 搜索与筛选

## 账户与基础设施

22. 经纪个人账户
23. 移动端 App（iOS + Android）
24. 本地优先 + 云端同步
25. 基础订阅付费

## AI 改进机制（现在就该记录，不需要额外开发）

MVP 阶段的编辑行为（经纪对 AI 草稿的每一次修改）本身就是有价值的信号：

```
AI 生成草稿
  -> 经纪编辑修改
    -> 修改记录被保存（架构文档中的 review_status / reviewed_by 字段已支持）
      -> 定期回顾"AI 常被修改的地方"
        -> 改进 Prompt
          -> 下一批草稿质量提升
```

这不是一个要现在开发的新功能，而是提醒：**MVP 阶段就应该有意识地收集和回顾这些编辑记录**，为持续改进 AI 输出质量提供依据。

# Phase 2A — Team Collaboration & Integrations（方向性规划，待 Phase 1 验证后决定）

**假设前提**：H1、H2 已被验证（经纪确实高频使用、愿意发送报告给客户）。

**目标**：从"个人效率工具"扩展为"团队/经纪公司工作流的一部分"。

## 团队协作

26. 团队工作空间（多个经纪归属同一 Workspace，如同一经纪公司/团队）
27. 团队品牌统一（团队级 logo、报告模板一致性）
28. 权限管理（管理员/普通成员角色区分）
29. 团队内房源历史共享（同团队不同经纪带看同一房源的记录互相可见）

## 外部工具集成（Integrations，不局限于 CRM）

30. 主流地产 CRM 数据同步（客户、房源信息双向同步）
31. 日历/带看排期集成
31a. 邮件集成（报告发送记录同步到邮箱往来）
31b. 云存储集成（原始媒体/报告归档到 Google Drive 等）

# Phase 2B — Buyer Portal（方向性规划，独立于 2A，执行前先做简化验证）

**假设前提**：Phase 2A 稳定运行。**执行顺序上，2B 应该先于完整账户系统，用最简方案验证需求：**

```
报告
 -> 安全分享链接（Phase 1 已有的 #16 功能）
   -> 买家打开查看
```

如果这个简单方案已经能满足买家侧的实际需求（打开率、停留时间等数据支撑），**完整的买家账户系统（登录、历史记录、互动功能）不必急于开发**，可以推迟甚至跳过。只有当简单链接方案明显不够用时，才进入以下功能：

32. 买家端登录入口（Buyer Portal）：买家可查看经纪主动分享给自己的多份报告历史
33. 买家对报告的评论/反应（买家可在具体观察条目下留言）
34. Offer 准备辅助：结构化带看记录直接引用进 offer 准备文档

## 分析与洞察

35. 经纪/团队使用分析仪表盘（报告生成量、发送率、买家打开率——这项数据同时也是判断是否需要 2B 完整账户系统的依据）
36. 语音指令扩展（更多结构化字段的快捷标注方式）

------------------------------------------------------------------------

# Phase 3 — 小范围分享实验（方向性规划，用于验证 H4，非全量功能）

**假设前提**：Phase 2 稳定运行，且有部分经纪明确表达分享意愿。

**目标**：以最小范围、可控的方式测试"经纪是否愿意半公开分享部分内容"，而不是直接上线公开功能。**依然遵守"默认私有"原则——这是可选的、经纪主动发起的实验，不是默认行为。**

37. 单份报告的分享开关（经纪逐份手动决定是否半公开，默认关闭）
38. 内容匿名化选项（去除经纪/买家身份信息后再分享）
39. 分享前的二次确认与同意流程
40. 分享内容的浏览/互动数据回传（用于判断分享内容是否真的被需要）
41. 同房源类型复用测试（针对同一栋公寓/同一开发商项目的可复用场景，见下方备注）
42. 分享内容的法律/合规审核流程（内部人工审核，非自动化）

> **备注（可复用房源类型）**：数据资产价值很可能集中在"可重复房源类型"（公寓大楼、联排别墅项目、同开发商量产户型），而非均匀分布在所有房产上。Phase 3 的实验应优先在这类房源上测试，而不是笼统地开放所有分享。

------------------------------------------------------------------------

# Phase 4 — 长期假设：更大规模的买家信息网络（仅在 Phase 3 验证成立后评估）

**假设前提**：Phase 3 证明确实有经纪愿意分享、且分享内容确实被买家需要/使用。

**目标**：从"经纪工具 + 小范围分享实验"演化为"买家决策信息网络"——这是一个条件性的长期方向，不是既定路线。（这个阶段的具体命名留待验证成立后再定，现阶段不需要纠结名字。）

43. 公开/半公开报告浏览与检索（买家可搜索特定房源/社区的历史带看记录）
44. 跨经纪房源历史聚合（同一房源被不同经纪多次带看的记录整合展示）
45. 内容贡献者收入分成机制
46. 信任/验证评分系统（GPS 一致性、带看时长、连续录制等——此前在 MVP 阶段明确排除的功能，只有在 Network 场景下才有必要）
47. 贡献者信誉体系
48. 面向数据公司/AI 公司的报告授权/API（作为潜在的 B2B 数据变现渠道）

# 商业模式附录（用于规划评估）

| 阶段 | 客户 | 收入模式 |
|---|---|---|
| Phase 1 | 个人买方经纪 | 订阅制 SaaS（按经纪个人付费）|
| Phase 2 | 经纪团队 | 按席位订阅（Seat-based SaaS）|
| Phase 3 | 经纪公司（Brokerage）| 企业级合同，可能包含合规审核服务费 |
| Phase 4 | 平台级（买家 / 数据公司 / AI 公司）| 平台交易分成 / 数据授权收入（假设阶段，未验证）|

**这张表本身也是假设，不是收入承诺**——尤其 Phase 3/4 的收入模式完全建立在对应阶段的功能被验证成立的前提上。

# 给规划评估的建议

- **只有 Phase 1 可以直接进入排期开发。**
- Phase 2-4 可以用于：估算长期人力/资金投入规模、向合伙人/投资人展示产品空间的完整性、内部讨论优先级——但不应作为对外承诺或客户沟通材料。
- 每进入下一阶段前，应先有上一阶段的真实验证数据支撑（对应 Customer Discovery Log / Experiment Log 里记录的结论），而不是按时间表自动推进。
- Phase 2 内部也遵循"先验证简单方案"的顺序：先用分享链接验证 Buyer Portal 的必要性，再决定是否投入完整账户系统。
